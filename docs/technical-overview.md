# PhysioMotion AI — Technical Overview

## What the Application Does

PhysioMotion AI is a desktop physiotherapy tool with two distinct user roles:

- **Physiotherapist Portal** — a physiotherapist creates exercises, records a short reference video, configures what to measure and what feedback to give, and clicks a button to generate an AI analysis module for that exercise.
- **Rehabilitation Assistant** — a patient selects an exercise, follows spoken instructions, performs it in front of the webcam, and receives spoken and written feedback after each round based on their measured movement quality.

All logic specific to how a movement is analysed (rep counting, feedback rules) is generated by an LLM and stored as Python source code in the database. The rest of the application is fixed infrastructure that runs that generated code safely.

## Directory and File Reference

### `main.py` — Application Entry Point

The root of the application. Creates the main `customtkinter` window, opens the SQLite connection, and owns all screen navigation.

**Navigation methods:**

| Method | Opens |
|---|---|
| `show_launcher()` | Splash screen |
| `show_exercise_list()` | Physiotherapist exercise list |
| `show_exercise_editor(exercise_id?)` | Create or edit an exercise |
| `show_code_viewer(exercise_id)` | Inspect generated analysis code |
| `show_client_exercise_list()` | Patient exercise selection |
| `show_exercise_preview(exercise_id)` | Watch reference video before starting |
| `show_session(exercise_id)` | Live exercise session |

Every screen is a `CTkFrame` subclass. Switching screens destroys the current frame and instantiates the new one. The single `sqlite3.Connection` is passed into every frame and service that needs it.

### `launcher/launcher_frame.py` — Splash Screen

Displays the title and two large tiles. Clicking a tile calls the appropriate navigation method on `main.py`. No business logic.

### `core/` — Shared Infrastructure

#### `core/pose_engine.py` — Real-Time Pose Detection

Wraps MediaPipe Pose. Runs in a daemon thread that:

1. Captures frames from the webcam with OpenCV.
2. Passes each frame through MediaPipe Pose, receiving 33 body landmarks with normalised (x, y, z, visibility) coordinates.
3. Calls `calculate_angles()` to compute all joint angles.
4. Constructs a `PoseFrame` dataclass.
5. Draws the skeleton overlay onto the frame.
6. Calls all registered subscriber callbacks with `(PoseFrame, annotated_frame)`.

`session_view.py` registers itself as a subscriber via `engine.subscribe(callback)` and unregisters on session end.

#### `core/angle_calculator.py` — Joint Angle Computation

Computes every angle needed by the application from a keypoints dict. All calculations use **x and y coordinates only** — the z (depth) axis from MediaPipe is discarded because it is too noisy for reliable angle measurement.

**Internal helpers:**

| Function | Purpose |
|---|---|
| `_angle_frontal_plane(a, b, c)` | Angle at point b using x,y. ~180° when straight, decreases as joint bends. Used for most joint angles. |
| `_trunk_lean_2d(a, b)` | Angle of vector a→b from vertical. 0°=upright, increases leaning. Reused for shin/thigh segment angles. |
| `_vector_to_horizontal_angle(a, b)` | Angle of vector from horizontal. Used for pelvic tilt, shoulder tilt. |
| `_signed_knee_valgus(hip, knee, ankle, side)` | Signed angular deviation of knee from hip-ankle line. 0°=collinear (straight). Positive=valgus (inward), negative=varus (outward). |

**`calculate_angles(keypoints)` output fields** (all available in `pose_data` inside generated modules):

| Group | Fields | Convention |
|---|---|---|
| Raw joint angles | `left/right_knee_angle`, `_hip_angle`, `_ankle_angle`, `_shoulder_angle`, `_elbow_angle`, `_wrist_angle`, `neck_angle`, `pelvic_tilt` | ~180°=straight, decreases with bend |
| HKA alignment | `left/right_hka_alignment` | Same as raw. Unsigned — use knee_valgus for direction. |
| Arm elevation | `left/right_arm_elevation` | Angle at shoulder from trunk to wrist. 0°=arm at side. |
| Bend values (preferred) | `left/right_knee_bend_2d`, `_elbow_bend_2d`, `_hip_bend_2d` | 0°=straight, increases with bend. Equals 180°−raw. |
| Trunk lean | `trunk_lean_angle`, `trunk_lean_2d` | 0°=upright. Side view=forward lean; front view=lateral lean. |
| Segment angles | `left/right_shin_angle`, `left/right_thigh_angle` | From vertical. 0°=segment vertical. Best from side view. |
| Bilateral tilt | `shoulder_tilt`, `pelvic_tilt` | 0°=level. Increases as one side is higher than the other. |
| Valgus | `left/right_knee_valgus` | Signed degrees. Positive=valgus(inward), negative=varus(outward). |
| Keypoints | `keypoints` | Dict of name→(x,y,z,visibility). x,y in [0,1], y increases downward. |

**Camera view guidance:**
- `[SIDE]` fields (shin_angle, thigh_angle) are only meaningful from a side-on camera. `shin_angle` is the only reliable indicator of knees-over-toes.
- `[FRONT]` fields (knee_valgus, shoulder_tilt, pelvic_tilt) require a front-facing camera.
- `[BOTH]` fields work from either view.

#### `core/data_contract.py` — PoseFrame Dataclass

A flat dataclass holding every field that `calculate_angles()` produces plus a `keypoints` dict and a `timestamp`. This is what travels from `pose_engine.py` to `session_view.py`. The `to_dict()` method converts it to a plain dict which is what generated module code receives as `pose_data`.

#### `core/module_validator.py` — Security Gate for Generated Code

Before any LLM-generated code is stored in the database it is passed through this validator. Uses Python's `ast` module to:

- Parse and syntax-check the code.
- Block any import of `os`, `sys`, `subprocess`, `socket`, `requests`, `urllib`, `http`, `shutil`.
- Confirm that the three required functions (`detect_rep`, `generate_round_feedback`, `get_session_summary`) are defined.

Returns `{"valid": bool, "error": str | None}`.

#### `core/video_analyzer.py` — Reference Video Analysis

Processes the physiotherapist's reference video (recorded during exercise setup) through MediaPipe to extract representative pose statistics. These statistics are optionally included in the LLM prompt to give the model a data-grounded description of what the exercise looks like in practice.

### `physio_app/` — Physiotherapist Portal

#### `physio_app/db.py` — Database Bootstrap

Called once at startup by `main.py`. Creates the SQLite file at `data/physiomotion.db`, enables foreign-key enforcement, and creates the four tables if they do not exist. Also runs schema migrations for databases created with earlier versions.

**Tables:**

| Table | Purpose |
|---|---|
| `exercises` | One row per exercise. Stores all physiotherapist-configured fields. |
| `analysis_modules` | One or more rows per exercise. Stores each version of generated code. |
| `sessions` | One row per completed patient session. Stores rep count, feedback log, summary. |
| `llm_logs` | Logs every prompt sent to and response received from the LLM API. |

#### `physio_app/services/exercise_service.py` — Exercise CRUD

All database reads and writes for exercises and their analysis modules go through this service. The `Exercise` dataclass is returned from every read operation.

**Key fields of `Exercise`:**

| Field | Type | Description |
|---|---|---|
| `id` | str (UUID) | Primary key |
| `name` | str | Human-readable exercise name |
| `camera_view` | str | `"front"`, `"side"`, or `"back"` |
| `client_instructions` | str | Spoken to patient before session starts |
| `llm_instructions` | str | Physiotherapist guidance on what to measure and what feedback to give |
| `boundary_values` | str | Quality targets (e.g. "knee bend: 90°"). Passed to LLM for feedback generation. |
| `display_values` | str | Which angles to show in the sidebar during the session |
| `session_duration_secs` | int | How long each exercise round runs in seconds |
| `reference_video_path` | str | Filesystem path to the recorded reference video |

Module management:
- `save_module(exercise_id, code)` — saves a new version, marks it active, deactivates the previous one.
- `get_active_module(exercise_id)` — returns the currently active module row (or `None` if none exists).

#### `physio_app/services/llm_service.py` — AI Code Generation

This is where the prompt is assembled and the Anthropic API is called.

**`build_prompt()`** assembles a prompt from:
- Exercise name and camera view
- Physiotherapist's client instructions, analysis instructions, boundary values, display values
- Session duration
- `_POSE_DATA_DESCRIPTION` — the full catalogue of available `pose_data` fields with their conventions, thresholds, and camera-view requirements
- `_FEW_SHOT` — a worked example module (bicep curl) the LLM uses as a structural template
- `_FUNCTION_SPEC_TEMPLATE` — the exact function signatures and contracts the generated module must implement
- Optional reference video statistics from `video_analyzer.py`

**`generate_module()`** calls the API, receives the generated Python source, validates it with `module_validator.py`, and if valid saves it to the database via `ExerciseService.save_module()`.

#### `physio_app/services/video_service.py` — Reference Video Recording

Provides `VideoRecorder`: captures from the webcam and writes frames to `data/exercises/<exercise_id>/reference.mp4`.

#### `physio_app/ui/exercise_list.py` — Exercise Browser (Physio)

Lists all exercises from the database. Buttons navigate to the editor or code viewer for each exercise.

#### `physio_app/ui/exercise_editor.py` — Exercise Editor

The main creation/editing screen. Contains:
- All exercise form fields (name, camera view, instructions, boundary values, display values, session duration)
- Live webcam preview and a "Record Reference Video" button (5-second countdown then 10-second capture)
- "Save & Generate Analysis" button — saves the exercise and triggers `LLMService.generate_module()` in a background thread, updating the UI with progress and result status.

#### `physio_app/ui/code_viewer.py` — Generated Code Inspector

Read-only view of the currently active analysis module code for an exercise. Used by physiotherapists to inspect or debug what was generated.

### `client_app/` — Rehabilitation Assistant

#### `client_app/services/session_service.py` — Session Orchestrator

The most complex service in the application. Manages the complete lifecycle of one exercise session:

**State machine:**

```
instructions → countdown → exercise → feedback → countdown → exercise → feedback → ...
```

On construction, it loads the exercise's active analysis module code and executes it in a **sandboxed namespace** using `exec()`. Only `math`, `statistics`, `collections`, `itertools`, and `functools` are available to the generated code. The extracted functions are stored as callables.

**`process_frame(pose_data)`** is called every frame by `session_view.py` and returns a result dict containing the current state and all display data. Internally it:
- In `exercise` state: calls `detect_rep(pose_data)` from the generated module, accumulates frames for feedback.
- On exercise window end: calls `generate_round_feedback(round_data)` from the generated module.
- Manages countdown timing and the `countdown_speak` signal for TTS.

**Generated functions called:**

| Function | When called | Purpose |
|---|---|---|
| `get_instructions()` | Session start | Returns spoken patient instructions |
| `detect_rep(pose_data)` | Every frame during exercise | Returns True once per rep |
| `reset_round()` | Before each exercise window | Resets phase state variables |
| `generate_round_feedback(round_data)` | After each exercise window | Returns list of feedback sentences |
| `get_session_summary(session_data)` | Session end | Returns overall summary sentences |
| `get_relevant_joints()` | Session start | Returns sidebar display pairs |

#### `client_app/services/tts_service.py` — Text-to-Speech

Wraps Windows PowerShell `System.Speech.Synthesis.SpeechSynthesizer` to speak text asynchronously. Provides:
- `speak(text)` — queues a message; latest wins (older queued messages are dropped).
- `speak_immediate(text)` — clears queue and speaks immediately.
- `is_speaking()` — polls whether TTS subprocess is still running.
- `stop()` — terminates current speech and clears queue. Called immediately when "End Session" or "← Home" is pressed.

#### `client_app/ui/exercise_list.py` — Exercise Browser (Client)

Lists exercises that have an active analysis module. Navigates to exercise preview on selection.

#### `client_app/ui/exercise_preview.py` — Reference Video Preview

Plays the physiotherapist's reference video so the patient can see the movement before starting. Navigates to session on confirmation.

#### `client_app/ui/session_view.py` — Live Session View

The main patient-facing screen during an exercise. Responsibilities:

1. **Camera display** — shows the annotated webcam feed (with pose skeleton overlay) at 768×576.
2. **State overlays** — draws countdown numbers, round info, and progress bar onto the video frame using OpenCV.
3. **Feedback panel** — when state=`feedback`, hides the camera and shows a black `CTkTextbox` panel with the round's feedback text. Hides when TTS finishes.
4. **Sidebar** — shows rep count, live joint values (from `get_relevant_joints()`), and current feedback status.
5. **TTS coordination** — polls `tts_service.is_speaking()` each frame to know when instructions have finished (triggering countdown start) and when feedback has finished (triggering next round).

**TTS race condition guard:** When feedback first appears, the UI must observe `is_speaking()=True` before it starts waiting for `is_speaking()=False`. This prevents the same frame that calls `speak_immediate()` from immediately ending the feedback state before the TTS subprocess has started.

**Joint value display conventions:**
- Fields in `_BEND_FIELDS` (raw angles like `left_knee_angle`) are displayed as `180 − value` so they show 0° when straight.
- Fields in `_VALGUS_FIELDS` (`left_knee_valgus`, `right_knee_valgus`) are displayed with a sign prefix: `+3.2°` for valgus, `-1.4°` for varus.
- All other fields are shown as-is with a `°` suffix.

## Where Dynamically Generated Code Lives

### In the database

Every time "Save & Generate Analysis" is clicked in the Physiotherapist Portal, the LLM generates a Python module. That module is stored as plain text in the `analysis_modules` table:

```
data/physiomotion.db
  └── analysis_modules
        ├── id          (UUID, primary key)
        ├── exercise_id (FK → exercises.id)
        ├── version     (integer, auto-incremented per exercise)
        ├── code        (full Python source as TEXT)
        ├── status      ("generated" or "validated")
        ├── is_active   (1 = currently in use, 0 = superseded)
        └── created_at
```

Multiple versions can exist per exercise (each time you regenerate, a new row is added and made active). The previous version is kept but marked `is_active=0`. You can inspect any version in the Code Viewer in the Physiotherapist Portal.

### At runtime

When a session starts, `SessionService` reads the active module's `code` field and executes it with `exec()` in a sandboxed namespace. The generated code never touches the filesystem — it runs entirely in memory for the duration of the session.

### Temporary file during validation

`core/module_validator.py` validates the code using Python's `ast` module (pure text parsing) — no temporary file is written to disk.

There is a `_tmp_module.py` file in the project root. This is a development artifact used for manually testing generated modules outside of the application and is not part of the production flow.

## Data Flow: End to End

### Physiotherapist flow

```
ExerciseEditorFrame
  → fills in: name, camera_view, instructions, boundary_values, display_values, duration
  → records reference video → saved to data/exercises/<id>/reference.mp4
  → clicks "Save & Generate"
      → ExerciseService.create() → exercises table
      → VideoAnalyzer.analyze_reference_video() → pose statistics
      → LLMService.build_prompt() → assembles full prompt
      → Anthropic API call → receives Python source code
      → module_validator.validate_module() → syntax + security check
      → ExerciseService.save_module() → analysis_modules table (is_active=1)
```

### Patient flow

```
ClientExerciseList → selects exercise
ExercisePreview → watches reference video
SessionView.__init__
  → ExerciseService.get_active_module() → reads code from analysis_modules table
  → SessionService.__init__() → exec(code) in sandbox
  → PoseEngine.start() → daemon thread begins webcam capture

Per frame (30fps):
  PoseEngine._run()
    → MediaPipe Pose → 33 landmarks
    → calculate_angles() → all joint angles
    → PoseFrame constructed
    → subscriber callback fired

SessionView._on_frame()
  → SessionService.process_frame(pose_data)
      → [exercise state] detect_rep(pose_data)  ← generated code
      → [feedback state] generate_round_feedback(round_data)  ← generated code
  → SessionView._update_ui() → camera display, overlays, sidebar, TTS

Session end:
  → SessionService.get_session_summary()  ← generated code
  → PoseEngine.stop()
  → TTSService.stop()
  → navigate back to launcher
```

## Key Design Decisions

**All angles are 2D.** MediaPipe's z-coordinate (depth) is discarded throughout. All `calculate_angles()` functions use x,y only. This makes measurements stable across different distances and lighting conditions.

**Generated code is isolated.** The `exec()` sandbox blocks filesystem access, network access, and system calls. Generated code can only use a whitelist of pure-Python standard library modules.

**Multiple module versions are preserved.** Regenerating an exercise creates a new `analysis_modules` row without deleting the old one. The physiotherapist can view past versions in the Code Viewer.

**Rep detection is separate from quality assessment.** `detect_rep()` uses loose thresholds to count any recognisable movement attempt. `generate_round_feedback()` then compares measured values against the physiotherapist's boundary values. This prevents the common failure mode where strict detection thresholds cause reps to not be counted when form is imperfect.

**TTS drives state transitions.** The instructions state does not end on a timer — it ends when the TTS subprocess finishes speaking. The feedback state also waits for TTS to complete before advancing to the next countdown. This keeps the audio and visual states synchronised regardless of instruction length.
