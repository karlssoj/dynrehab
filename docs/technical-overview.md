# PhysioMotion AI — Detailed Technical Documentation

## Purpose

PhysioMotion AI is a Windows desktop application for physiotherapy exercise guidance. It has two distinct user modes:

- **Physiotherapist Portal** — a clinician creates exercises, records a reference video, writes instructions and quality criteria, and clicks a button to generate an AI analysis module that knows how to count reps and give feedback for that specific exercise.
- **Rehabilitation Assistant** — a patient selects an exercise, watches the reference video, then performs the exercise in front of the webcam while the application counts reps in real time, shows live joint measurements in a sidebar, and delivers spoken and written feedback after each round.

The central design idea is that the movement analysis logic is not hardcoded. Every exercise has its own small Python module, generated by an LLM, that implements how to detect reps and what feedback to give. The rest of the application is fixed infrastructure that runs that generated code safely.

---

## Application Startup

`main.py` is the entry point. Running it:

1. Calls `load_dotenv()` to read the `.env` file, which contains the Anthropic API key.
2. Calls `init_db()` from `physio_app/db.py`, which creates `data/physiomotion.db` if it does not exist, creates the four database tables, and runs any pending schema migrations. Returns an open `sqlite3.Connection`.
3. Creates a `PhysioMotionApp` instance, which is a `customtkinter` top-level window at 1100×700 pixels.
4. `PhysioMotionApp.__init__` immediately calls `show_launcher()`, which displays the splash screen.
5. `app.mainloop()` runs until the window is closed, at which point the database connection is closed.

### Screen Navigation

`PhysioMotionApp` is the navigation hub. It holds one active frame at a time in `self._current_frame`. The `_switch_frame(frame_class, **kwargs)` method destroys the current frame and instantiates the new one, passing `self` (the app) and `self.db_conn` (the database connection) as the first two arguments, plus any keyword arguments specific to that screen.

Every screen frame has a reference to `self.app` pointing back to the `PhysioMotionApp`, which it uses to navigate to other screens.

```
show_launcher()              → launcher/launcher_frame.py :: LauncherFrame
show_exercise_list()         → physio_app/ui/exercise_list.py :: ExerciseListFrame
show_exercise_editor(id?)    → physio_app/ui/exercise_editor.py :: ExerciseEditorFrame
show_code_viewer(id)         → physio_app/ui/code_viewer.py :: CodeViewerFrame
show_client_exercise_list()  → client_app/ui/exercise_list.py :: ClientExerciseListFrame
show_exercise_preview(id)    → client_app/ui/exercise_preview.py :: ExercisePreviewFrame
show_session(id)             → client_app/ui/session_view.py :: SessionViewFrame
```

## Database (`physio_app/db.py`)

The database is a single SQLite file at `data/physiomotion.db`. `init_db()` opens a connection with `check_same_thread=False` (needed because the TTS and camera threads read through the same connection), sets `row_factory = sqlite3.Row` (so rows behave like dicts), enables foreign key enforcement, and calls `_create_tables()` and `_migrate()`.

### Tables

**`exercises`** — one row per exercise created by the physiotherapist.

| Column | Type | Description |
|---|---|---|
| `id` | TEXT (UUID) | Primary key, generated at creation time |
| `name` | TEXT | Human-readable exercise name |
| `camera_view` | TEXT | `"front"`, `"side"`, or `"back"` |
| `client_instructions` | TEXT | Spoken to patient before the session starts |
| `llm_instructions` | TEXT | Physiotherapist guidance on what to measure and what feedback to give — this goes into the LLM prompt |
| `boundary_values` | TEXT | Quality targets (e.g. `"knee bend: 90°, trunk lean: 30°"`) — these go into the LLM prompt as feedback targets |
| `display_values` | TEXT | Which angle fields to show in the sidebar during the session |
| `session_duration_secs` | INTEGER | How many seconds each exercise round lasts (default 10) |
| `reference_video_path` | TEXT | Path to the recorded `.mp4` reference video |
| `created_at` | DATETIME | Row creation timestamp |

**`analysis_modules`** — one or more rows per exercise; each row is one version of a generated Python module.

| Column | Type | Description |
|---|---|---|
| `id` | TEXT (UUID) | Primary key |
| `exercise_id` | TEXT | Foreign key → `exercises.id`, cascades on delete |
| `version` | INTEGER | Auto-incremented per exercise; first generation = 1 |
| `code` | TEXT | Complete Python source of the analysis module |
| `status` | TEXT | `"generated"` after creation, `"validated"` if manually reviewed |
| `is_active` | INTEGER | `1` = currently in use; `0` = superseded by a newer version |
| `created_at` | DATETIME | Generation timestamp |

Multiple versions of a module are kept. Every time the physiotherapist clicks "Save & Generate", a new row is added with `is_active=1` and all previous rows are set to `is_active=0`. Old versions can be viewed in the Code Viewer.

**`sessions`** — one row per completed patient session.

| Column | Description |
|---|---|
| `id` | UUID primary key |
| `exercise_id` | Which exercise was performed |
| `started_at` / `ended_at` | Session timestamps |
| `rep_count` | Total reps across all rounds |
| `feedback_log` | JSON array of feedback strings |
| `session_summary` | End-of-session summary text |

**`llm_logs`** — records every prompt and response from the Anthropic API, for auditing and debugging.

### Schema Migrations

`_migrate()` checks whether the `client_instructions` column exists in the `exercises` table. If not, the database predates that column, and the migration adds all missing columns. Because SQLite does not support column removal and the old schema is structurally incompatible, all existing data is cleared first (exercises, modules, sessions, logs). This is a one-time destructive migration; once the columns exist it does nothing.

## Physiotherapist Portal

### Exercise List (`physio_app/ui/exercise_list.py`)

Queries `ExerciseService.list_all()` and displays one row per exercise with its name, camera view, and buttons to edit or view the generated code. A "New Exercise" button navigates to the editor with no `exercise_id`.

### Exercise Editor (`physio_app/ui/exercise_editor.py`)

The main creation and editing screen. It is split into a scrollable left column (form fields), a right column (webcam preview and record controls), and a bottom bar with the "Save & Generate" button.

**Form fields:**
- Exercise name
- Camera view (dropdown: `front` / `side` / `back`)
- Client instructions — what is spoken to the patient at the start
- Analysis instructions — tells the LLM what movements constitute a rep, what quality criteria to check, and what coaching language to use
- Boundary values — specific thresholds (e.g. `"knee bend should reach 90°"`) used by the LLM as quality targets in the feedback function
- Display values — which measurement fields to show in the patient-facing sidebar
- Session duration in seconds

**Reference video recording:**

The physiotherapist clicks "Record Reference Video". A 5-second on-screen countdown runs (drawn onto the live webcam feed), then `VideoService.VideoRecorder` starts and records 10 seconds to `data/exercises/<exercise_id>/reference.mp4`. The live feed continues to show in the right column at all times.

**Saving and generating:**

When "Save & Generate Analysis" is clicked:

1. All form fields are read.
2. `ExerciseService.create()` or `.update()` writes the exercise to the database.
3. `VideoAnalyzer.analyze_reference_video()` processes the reference video through MediaPipe and returns summary statistics (average and range of each joint angle across the recording). This gives the LLM real data about what the exercise looks like.
4. `LLMService.generate_module()` is called in a background thread so the UI stays responsive. The UI shows "Generating analysis code…" while waiting.
5. On success: "✓ Code generated successfully" in green. On failure: "✗ Generation failed" in red with the error message.

### Code Viewer (`physio_app/ui/code_viewer.py`)

Read-only view of the raw Python source of the active analysis module for an exercise. Used by physiotherapists to inspect, understand, or debug what was generated.

## LLM Code Generation (`physio_app/services/llm_service.py`)

This is where the exercise-specific intelligence is created. `generate_module()` calls `build_prompt()` to assemble the full prompt, sends it to `claude-opus-4-5` via the Anthropic API, validates the response, and if valid stores it.

### What Goes Into the Prompt

`build_prompt()` assembles these sections in order:

**1. Exercise metadata** — name, camera view (`"front"` / `"side"` / `"back"`), client instructions, analysis instructions, boundary values, display values, session duration.

**2. `_POSE_DATA_DESCRIPTION`** — the complete catalogue of every field available in `pose_data` at runtime, with their units, conventions, and which camera view they are useful for. Key groups:

- Raw joint angles (`left_knee_angle` etc.) — ~180° when straight, decreases with bend.
- Bend values (`left_knee_bend_2d` etc.) — inverse of raw; 0° = straight, increases with bend. These are preferred.
- Segment angles (`left_shin_angle`, `left_thigh_angle`) — angle of that bone segment from vertical. Only meaningful from a side-view camera.
- Signed valgus angle (`left_knee_valgus`) — angular deviation of knee from hip-ankle line. 0° = aligned; positive = knee caving inward (valgus); negative = bowing outward (varus). Only useful from a front-view camera.
- Bilateral tilt (`shoulder_tilt`, `pelvic_tilt`) — how level the two landmarks are. Front view only.
- `keypoints` dict — raw `(x, y, z, visibility)` tuples for all 33 MediaPipe landmarks, for cases where a pre-computed angle is insufficient.

The description also includes two ready-to-copy helper functions the generated code may paste in:
- `_pelvic_tilt_2d(pose_data)` — computes pelvic tilt from keypoints for front-view exercises (the pre-computed `pelvic_tilt` field reads ~180° when facing front and is unusable).
- `_angle_2d(ax, ay, bx, by, cx, cy)` — computes any arbitrary 2D angle at point B, for cases where no pre-computed field covers the needed angle.

**3. `_FEW_SHOT`** — a complete, working example module (double-pole skiing from a side camera). This is the most important prompt section for getting correct code structure. The LLM is told to follow the same structure.

**4. `_FUNCTION_SPEC_TEMPLATE`** — the exact signatures and detailed requirements for the five functions the generated module must implement (see "Generated Module Contract" section below).

**5. Reference video data** (if a reference video was recorded) — MediaPipe-extracted statistics from the physiotherapist's demonstration video, e.g. `"left_knee_bend_2d: min=2.1°, max=88.4°"`. This grounds the LLM's thresholds in actual measured data rather than guesswork.

**6. Rules** — hard constraints applied to every generated module, including: no banned imports, use the pre-computed valgus fields rather than recomputing from keypoints, do not use `abs()` on valgus (the sign encodes direction), do not attempt knees-over-toes detection from a front-view camera, use `_pelvic_tilt_2d` instead of the raw pelvic_tilt field on front-view exercises, and always give at least one specific positive observation in feedback.

### Validation and Storage

The API response text is passed to `module_validator.validate_module()`. If valid, `ExerciseService.save_module()` stores it. If invalid (syntax error, banned import, missing function), the error is shown in the editor and nothing is stored.

---

## Security Validation (`core/module_validator.py`)

Before any generated code is stored, `validate_module(code)` runs three checks:

1. **Syntax** — `ast.parse(code)` must not raise `SyntaxError`.
2. **Banned imports** — walks the AST looking for `Import` and `ImportFrom` nodes. If any top-level module name is in `{"os", "subprocess", "sys", "shutil", "socket", "requests", "urllib", "http"}`, the module is rejected.
3. **Required functions** — checks that `detect_rep`, `generate_round_feedback`, and `get_session_summary` are defined at module level.

Returns `{"valid": bool, "error": str | None}`.

Note: this is a static check only. The runtime sandbox in `SessionService._load_module()` is the enforcement layer — even if a module passed validation, the `exec()` environment would still block any attempt to import a banned module at runtime.

## Rehabilitation Assistant

### Client Exercise List (`client_app/ui/exercise_list.py`)

Shows only exercises that have an active analysis module (i.e. exercises that have been successfully generated). Exercises without a module are not shown because they cannot run. Clicking an exercise navigates to the preview screen.

### Exercise Preview (`client_app/ui/exercise_preview.py`)

Plays the physiotherapist's recorded reference video in a loop so the patient can see what the movement looks like before starting. A "Start Session" button navigates to the live session.

### Session View (`client_app/ui/session_view.py`)

The main patient-facing screen during an exercise session. It wires together the pose engine, the session service, and the TTS service, and handles all UI rendering.

**On construction** (`__init__` → `_start_session`):

1. Reads the exercise from the database (`ExerciseService.get(exercise_id)`).
2. Reads the active analysis module (`ExerciseService.get_active_module(exercise_id)`).
3. Creates `SessionService` with the module code.
4. Calls `session_service.get_instructions()` — if instructions exist, speaks them immediately with `tts.speak_immediate()` and sets `_instructions_spoken = True`.
5. Calls `session_service.get_relevant_joints()` and builds one label row per joint in the sidebar.
6. Registers `_on_frame` as a subscriber on `PoseEngine` and calls `engine.start()`.

**Layout:**

The screen uses a two-column grid. Column 0 (weight 3) holds the camera display. Column 1 (weight 1) holds the sidebar with rep count, joint value labels, and a text feedback label. The feedback panel occupies the same grid cell as the camera display (column 0) and is swapped in/out by calling `grid_remove()` on whichever one should be hidden.

**Per-frame flow:**

`PoseEngine` calls `_on_frame(pose_frame, annotated_frame)` from its background thread approximately 30 times per second. This method:

1. Calls `session_service.process_frame(pose_frame.to_dict())` — returns a result dict describing the current state.
2. Schedules `_update_ui(result, annotated_frame, pose_frame)` on the main thread via `self.after(0, ...)`, because tkinter is not thread-safe.

`_update_ui` does all visual rendering. It branches on `result["state"]`:

- **`instructions`** — draws a semi-transparent dark overlay on the camera frame with the text "Listening to instructions...". Polls `tts.is_speaking()` each frame; as soon as TTS finishes, calls `session_service.start_countdown()` (which was delayed until speech completed).
- **`countdown`** — draws a dark overlay and a large countdown number (5, 4, 3, 2, 1) centred on the frame. When the count number changes, signals TTS to speak it. When it reaches 0, speaks "Go!".
- **`exercise`** — draws the round number, rep count, remaining time, and a progress bar at the bottom of the frame. Updates the sidebar with live joint values.
- **`feedback`** — hides the camera and shows the black `CTkTextbox` feedback panel with the round's feedback text.

**TTS race condition guard:**

When the state transitions to `feedback`, `speak_immediate()` is called with the feedback text. But `is_speaking()` checks whether the PowerShell subprocess is still running, and on the same frame that `speak_immediate()` is called, the subprocess may not have started yet — so `is_speaking()` would return `False`, which would immediately end the feedback state before the patient heard anything. The fix uses two flags:

- `_feedback_tts_started` — set to `True` the first frame that `is_speaking()` returns `True`.
- `_feedback_end_scheduled` — set to `True` the first frame that `_feedback_tts_started` is `True` and `is_speaking()` returns `False`.

Only when both conditions are met in sequence is `session_service.end_feedback()` called.

**Joint value display:**

The sidebar shows one label pair (name + value) per joint returned by `get_relevant_joints()`. Values are refreshed each frame during the `exercise` state. Display conventions:
- Fields in `_BEND_FIELDS` (raw angles like `left_knee_angle`) are displayed as `180 − value`, converting them to 0°=straight.
- Fields in `_VALGUS_FIELDS` (`left_knee_valgus`, `right_knee_valgus`) are displayed with a sign prefix: `+3.2°` for valgus inward, `-1.4°` for varus outward.
- All other fields are displayed as-is with a `°` suffix.

**Ending the session:**

Both "← Home" and "End Session" call `_tts.stop()` (clearing the queue and terminating any running TTS subprocess immediately) and `_engine.stop()` and `_engine.unsubscribe(self._on_frame)` before navigating away.

## Pose Detection (`core/pose_engine.py`)

`PoseEngine` is a subscriber-pattern wrapper around MediaPipe Pose. It runs entirely in a daemon thread.

**Thread lifecycle:**

`start(camera_index=0)` creates and starts a daemon thread running `_run(camera_index)`. `stop()` sets `self._running = False`, which causes the `while self._running` loop to exit and the thread to terminate.

**`_run()` inner loop:**

Each iteration:

1. `cap.read()` — reads one BGR frame from the webcam.
2. Converts to RGB, sets `writeable = False` (required by MediaPipe for performance), runs `pose.process(rgb)`.
3. Extracts 33 landmarks from `results.pose_landmarks.landmark`. Each landmark is stored as `(x, y, z, visibility)` in the `keypoints` dict, keyed by the landmark name from `LANDMARK_NAMES`.
4. Calls `calculate_angles(keypoints)` from `core/angle_calculator.py`, which returns a flat dict of angle names to float values.
5. Sets each angle onto the `PoseFrame` dataclass using `setattr`.
6. Calls `_draw_overlay()` to add the green skeleton and joint dots to the frame. Joints in `_highlight_joints` are drawn red instead of white.
7. Notifies all subscribers with `(pose_frame, annotated_frame)`, catching and silently ignoring any exceptions from subscriber callbacks.

**Thread safety:**

The subscriber list and `_highlight_joints` set are read and modified under `self._lock`. The subscriber list is copied under the lock before iterating, so a subscriber can safely unsubscribe itself inside its callback.

**MediaPipe configuration:**

```python
mp.solutions.pose.Pose(
    min_detection_confidence=0.5,
    min_tracking_confidence=0.5,
    model_complexity=1,
)
```

`model_complexity=1` is the balanced model — more accurate than 0 but faster than 2.

## Angle Calculation (`core/angle_calculator.py`)

All angles are computed from **x and y coordinates only**. The z coordinate from MediaPipe (depth) is dropped because its accuracy is insufficient for clinical measurement at normal camera distances.

**Coordinate system:** MediaPipe normalises x and y to [0, 1]. x increases to the right. y increases downward (top of image = 0, bottom = 1). For a front-facing camera the patient's left body side appears on the right side of the image (higher x).

### Helper Functions

**`_angle_frontal_plane(a, b, c)`** — computes the angle at point B formed by vectors B→A and B→C, using x,y only. Returns approximately 180° when the three points are collinear (joint straight), and decreases as the joint bends. Used for most joint angles.

**`_trunk_lean_2d(a, b)`** — computes the angle of the vector a→b relative to vertical (pointing straight up in image coordinates, which is the (0, −1) direction). Returns 0° when the vector is exactly vertical, and increases as it tilts in any direction. This function is reused for:
- Trunk lean (hip midpoint → shoulder midpoint)
- Shin angle (ankle → knee): 0° = shin vertical, increases as knee travels forward
- Thigh angle (knee → hip): 0° = standing upright, ~90° = thigh horizontal (parallel squat)

**`_vector_to_horizontal_angle(a, b)`** — angle of a vector from horizontal. Used for pelvic tilt and shoulder tilt. Returns 0° when level, increases as one end is higher.

**`_signed_knee_valgus(hip, knee, ankle, side)`** — measures the angular deviation of the knee from the hip-ankle line in the frontal plane.

- **Magnitude**: `180° − _angle_frontal_plane(hip, knee, ankle)`. This is 0° when the three points are collinear (perfect alignment), and increases as the knee moves off the line in either direction.
- **Sign**: determined by the 2D cross product of (hip→ankle) × (hip→knee). For the left leg, a positive cross product means the knee is to the left of the hip-ankle vector, which on a front-facing camera means medially inward (valgus) → positive. For the right leg the sign is inverted. Result: positive = valgus (knee caving inward), negative = varus (knee bowing outward).

**`calculate_angles(keypoints)`** calls all helpers and returns every pre-computed field as a flat dict. This dict maps directly onto the `PoseFrame` dataclass fields and is what generated module code receives as `pose_data`.

## Data Contract (`core/data_contract.py`)

`PoseFrame` is a Python dataclass with one field per angle output of `calculate_angles()`, plus `timestamp` and `keypoints`. All angle fields default to `0.0`.

`to_dict()` calls `dataclasses.asdict()`, which recursively converts the dataclass (including the nested `keypoints` dict) to a plain Python dict. This is what `session_service.process_frame()` receives and what gets stored in `_round_frames` for feedback generation.

## Session Service (`client_app/services/session_service.py`)

`SessionService` owns the exercise session state machine and is the only point where generated code is executed.

### Sandbox Setup

`_load_module(code)` creates a namespace dict with `__builtins__` set to `SAFE_BUILTINS` — a hand-curated whitelist of safe Python builtins:

```python
SAFE_BUILTINS = {
    "abs", "all", "any", "bool", "dict", "enumerate", "float", "int",
    "len", "list", "max", "min", "print", "range", "round", "set",
    "str", "sum", "tuple", "zip", "isinstance", "issubclass", "type",
    "hasattr", "getattr", "None", "True", "False",
}
```

`__import__` is replaced with `_make_safe_import()`, which wraps the real import function but raises `ImportError` for any module not in `{"math", "statistics", "collections", "itertools", "functools"}`.

`exec(code, namespace)` runs the generated module in this restricted environment. After execution, the five function names are extracted from the namespace:

```python
self._detect_rep            = namespace["detect_rep"]           # required
self._generate_round_feedback = namespace["generate_round_feedback"]  # required
self._get_session_summary   = namespace.get("get_session_summary")    # required but optional lookup
self._get_instructions      = namespace.get("get_instructions")       # optional
self._reset_round           = namespace.get("reset_round")            # optional
self._get_relevant_joints   = namespace.get("get_relevant_joints")    # optional
```

These are now ordinary Python callables stored as instance attributes.

### State Machine

```
"instructions"  →  (TTS done)  →  "countdown"
"countdown"     →  (5s elapsed)  →  "exercise"
"exercise"      →  (duration elapsed)  →  "feedback"
"feedback"      →  (TTS done, end_feedback called)  →  "countdown"
```

The session loops indefinitely through countdown → exercise → feedback until the patient ends it.

`process_frame(pose_data)` is called on every camera frame and drives the state machine:

- **`instructions`** — does nothing in the service; the view handles TTS and calls `start_countdown()` when ready.
- **`countdown`** — computes `remaining = COUNTDOWN_SECS (5) − elapsed`. When the integer value of `math.ceil(remaining)` changes, sets `result["countdown_speak"]` to that number (or 0 for "Go!") so the view can speak it. After 5.5 seconds total, calls `_enter_exercise()`.
- **`exercise`** — appends `pose_data` to `_round_frames`, calls `self._detect_rep(pose_data)` from generated code, increments rep count if it returns `True`. After `exercise_secs` have elapsed, calls `_enter_feedback()` which calls `self._generate_round_feedback(round_data)` from generated code and returns the feedback lines.
- **`feedback`** — waits. The view calls `end_feedback()` when TTS finishes, which transitions back to `countdown`.

### Angle Statistics

`process_frame` also accumulates `_angle_stats` — a dict tracking the per-session `min` and `max` of every numeric `pose_data` field (excluding values ≤ 5° as noise). This is passed to `get_session_summary()` so the generated code can report what range of movement the patient achieved across the whole session.

## Generated Module Contract

Every generated module must implement these functions. The session service calls them at the times described.

### `get_instructions() → list[str]` *(optional)*

Called once at session start. Returns 1–2 short sentences telling the patient how to position themselves relative to the camera and what movement to perform. The sentences are joined and spoken aloud via TTS before the first countdown.

If not defined, the session skips the instructions state and goes directly to countdown.

### `detect_rep(pose_data: dict) → bool` *(required)*

Called on every camera frame during the exercise window (~30 times per second). Returns `True` exactly once when a complete rep has been detected; `False` otherwise.

This function must implement a phase state machine using module-level variables. Example for a squat:

```python
_phase = "ready"      # "ready" | "squatting"
_SQUAT_START = 30     # knee_bend_2d > this → squat begins
_SQUAT_RETURN = 15    # knee_bend_2d < this → rep counted

def detect_rep(pose_data):
    global _phase
    bend = pose_data["left_knee_bend_2d"]
    if _phase == "ready" and bend > _SQUAT_START:
        _phase = "squatting"
    elif _phase == "squatting" and bend < _SQUAT_RETURN:
        _phase = "ready"
        return True
    return False
```

**Critical rule**: the detection thresholds must be loose anatomical thresholds (e.g. "any knee bend over 20° counts as a squat attempt"). They must NOT use the physiotherapist's boundary values (e.g. "knee should reach 90°") as gates, because a patient who performs a shallow squat must still have a rep counted so that `generate_round_feedback` can give them corrective coaching.

### `reset_round()` *(optional)*

Called before each exercise window starts. Must reset all module-level state variables (phase, counters, deques) back to their initial values.

### `generate_round_feedback(round_data: dict) → list[str]` *(required)*

Called once after each exercise window ends. `round_data` contains:

```python
{
    "round_number": int,           # which round just finished (1-based)
    "rep_count": int,              # reps counted this round
    "frames": list[dict],          # all pose_data frames from this round
    "duration_seconds": float,     # how long the round was
}
```

Returns a list of 2–4 strings which are displayed in the feedback panel and spoken aloud. Typical implementation pattern:

1. Extract the relevant angle measurements from `frames` (e.g. the maximum knee bend reached in any frame, the average valgus angle).
2. Compare against the physiotherapist's boundary values.
3. Open with rep count and one specific positive observation based on actual measurements.
4. Add corrective cues only for issues that actually occurred.
5. Return the list.

The feedback sentences must be appropriate for spoken delivery — no raw angle values unless explicitly requested by the physiotherapist.

### `get_session_summary(session_data: dict) → str` *(required)*

Called once when the patient ends the session. `session_data` contains:

```python
{
    "total_reps": int,
    "rounds": [...],               # list of round_data dicts from all rounds
    "duration_seconds": float,     # total elapsed time
    "angle_stats": {               # per-session min/max for every angle
        "left_knee_bend_2d": {"min": 2.1, "max": 88.4},
        ...
    }
}
```

Returns a single string of 2–4 sentences summarising the session.

### `get_relevant_joints() → list` *(optional)*

Called once at session start. Returns a list of `(display_label, pose_data_key)` pairs. The `pose_data_key` must be a key that exists in `pose_data`. Display labels should be 12 characters or shorter.

Example:
```python
def get_relevant_joints():
    return [
        ("L knee",  "left_knee_bend_2d"),
        ("R knee",  "right_knee_bend_2d"),
        ("L valgus", "left_knee_valgus"),
    ]
```

The session view uses these to build sidebar label rows and to update them on every frame during the exercise state.

## Text-to-Speech (`client_app/services/tts_service.py`)

TTS is implemented using the Windows PowerShell `System.Speech.Synthesis.SpeechSynthesizer`. Each speech request launches a PowerShell subprocess that speaks the text synchronously, then exits.

**`speak(text)`** — drops any existing queued message and enqueues this one. Only the most recent message is ever spoken; older ones are silently discarded. This is the "latest wins" behaviour used for countdown numbers (3, 2, 1 — if the user is slow, only the current number matters).

**`speak_immediate(text)`** — clears the queue, terminates any running subprocess, and puts the new text at the front of the queue. Used for instructions and feedback, which must be heard in full.

**`is_speaking()`** — returns `True` if the PowerShell subprocess is still running (`proc.poll() is None`).

**`stop()`** — drains the queue and calls `proc.terminate()` on the running subprocess. Called immediately when the patient presses "← Home" or "End Session" so audio stops before the screen changes.

A background worker thread runs the queue and manages the subprocess lifecycle.

## Reference Video Analysis (`core/video_analyzer.py`)

`analyze_reference_video(video_path)` opens the reference video file with OpenCV and runs MediaPipe Pose on every frame, collecting all angle values. Returns a dict summarising the range seen for each angle (min, max, and whether it showed meaningful variation). This data is formatted by `_format_reference_data()` in `llm_service.py` and appended to the prompt so the LLM has measured data about what the exercise actually looks like, rather than having to guess thresholds from the exercise name alone.

## Where Generated Code Is Stored and Executed

### Storage (database)

Generated Python source code is stored as plain text in `analysis_modules.code`. The database is at `data/physiomotion.db`. To inspect any version, use the Code Viewer in the Physiotherapist Portal, or query the database directly:

```sql
SELECT version, is_active, code
FROM analysis_modules
WHERE exercise_id = '<exercise_uuid>'
ORDER BY version;
```

### Execution (in-memory sandbox)

When `SessionService.__init__` is called, the active module's `code` string is executed with:

```python
namespace = {"__builtins__": SAFE_BUILTINS}
exec(code, namespace)
```

The code never touches the filesystem. It runs in the Python process memory for the duration of the session and is garbage-collected when `SessionService` is discarded (on session end). There is no temporary file involved.

## Complete Data Flow Diagrams

### Physiotherapist Creates an Exercise

```
ExerciseEditorFrame
    │
    ├─ fill form fields (name, camera_view, instructions, boundary_values, ...)
    ├─ record reference video
    │       VideoService.VideoRecorder
    │       → writes data/exercises/<id>/reference.mp4
    │
    └─ click "Save & Generate"
            │
            ├─ ExerciseService.create()
            │       → INSERT INTO exercises
            │
            ├─ VideoAnalyzer.analyze_reference_video(path)
            │       → opens .mp4 with OpenCV
            │       → runs MediaPipe Pose on each frame
            │       → returns angle statistics dict
            │
            ├─ LLMService.build_prompt(...)
            │       → assembles exercise fields + _POSE_DATA_DESCRIPTION
            │            + _FEW_SHOT + _FUNCTION_SPEC_TEMPLATE + ref stats
            │
            ├─ Anthropic API call (claude-opus-4-5)
            │       → returns Python source code as text
            │
            ├─ module_validator.validate_module(code)
            │       → AST parse, banned import check, required function check
            │
            └─ ExerciseService.save_module(exercise_id, code)
                    → INSERT INTO analysis_modules (version N, is_active=1)
                    → UPDATE analysis_modules SET is_active=0 (all prior)
```
